### Document Schema Design

#### `user_profiles` — The Central Document

Each user profile is a **single document** that serves as the hub for all three use cases. ASP pipelines write fraud state into it, the screening service flags matches on it, and the analytics chatbot queries it. This is a deliberate schema choice — keeping everything in one document means `$lookup` joins from ASP and single-document updates from screening are both fast and atomic.

Key design decisions:
- **`fraud.signals`** is a nested object keyed by signal ID. ASP pipeline S01a writes directly into `fraud.signals.s01` using `$merge` with `whenMatched: "merge"` — this means it only touches the S01 sub-field without overwriting other signal state.
- **`fraud.embedding`** stores the 1024-dimensional Voyage AI vector directly on the user document. Atlas Vector Search indexes this field for similarity queries.
- **`fraud.lastTopupAt`** is written by the topup-state-writer ASP processor on every top-up event. Pipelines S01b, S02, and S03 read this via `$lookup` to check for recent top-up activity.
- **`screening.matches[]`** grows as batch sweeps find hits. Each match records the sanctioned name, source list, relevance score, and detection timestamp.

## Atlas Stream Processing — The Fraud Signal Pipelines

All processors read from a single Kafka topic (`FuelRetail-fraud-events`) via the `UtilitymskKafkaConnection` source connection and write back to MongoDB Atlas via the `FuelRetail_cluster` sink connection. There are also two supporting processors (event-ingest and topup-state-writer) not shown here — they handle event storage and top-up state tracking respectively.

The 4 signal pipelines below are the core fraud detection logic. They demonstrate two key ASP patterns:
- **Windowed aggregation**: Group events over time intervals, then act on aggregates (S01a, S03, S04)
- **Windowless enrichment**: Enrich each event with stored state via `$lookup`, then decide per-event (S01b, S02)

### How the pipelines interact with MongoDB

The pipelines don't just read from Kafka and write alerts. They **read and write existing MongoDB documents** as part of their processing:

```
                    ┌─────────────────────────────────────────────────┐
                    │              user_profiles collection           │
                    │                                                 │
  topup-state-writer ──writes──▶  fraud.lastTopupAt                  │
  S01a ──────────────writes──▶  fraud.signals.s01.topupBurstDetected │
                    │                                                 │
  S01b ◀──reads ($lookup)────  fraud.signals.s01.*                   │
  S02  ◀──reads ($lookup)────  fraud.lastTopupAt                     │
  S03  ◀──reads ($lookup)────  fraud.lastTopupAt                     │
                    └─────────────────────────────────────────────────┘

                    ┌─────────────────────────────────────────────────┐
                    │              fraud_alerts collection            │
                    │                                                 │
  S01b ──writes ($merge)──▶  { signal: "S01", severity: "critical" } │
  S02  ──writes ($merge)──▶  { signal: "S02", severity: "high" }     │
  S03  ──writes ($merge)──▶  { signal: "S03", severity: "high" }     │
  S04  ──writes ($merge)──▶  { signal: "S04", severity: "medium" }   │
                    │                                                 │
  Change Stream ◀──watches──  operationType: "insert"                │
                    └─────────────────────────────────────────────────┘
```

This is the key architectural advantage over KSQL: ASP processors can **read from and write to existing MongoDB collections** mid-stream using `$lookup` and `$merge`, enabling stateful cross-event correlation without an external database layer.

### Signal S01 — Top-Up Cluster + Instant Transfer Transfer Out (Two-Stage)

**What it detects**: A user rapidly tops up their wallet 2+ times with large amounts (>= RM500), then immediately transfers the money out via InstantTransfer. Classic "top-up-and-cash-out" pattern used in card fraud and money laundering.

**Why two stages**: You can't detect this in a single pipeline because the top-up cluster and the transfer-out are different event types that need different processing:
- **S01a** (windowed) aggregates top-ups over time to detect the cluster
- **S01b** (windowless) checks each transfer-out against the stored cluster state

#### S01a — Top-Up Cluster Detection (Windowed)

```
MSK → filter auto_topup >= RM500 → [1-min tumbling window] → group by user →
  count >= 2? → compute interval → $merge → user_profiles.fraud.signals.s01
```

**How it reads/writes**: S01a doesn't read any existing documents. It writes intermediate detection state INTO the `user_profiles` collection using `$merge` with `whenMatched: "merge"`. This means it updates the existing user profile document by merging in new fields under `fraud.signals.s01`, without overwriting the rest of the profile.

**What gets written to user_profiles**:
```json
{
  "fraud": {
    "signals": {
      "s01": {
        "topupBurstDetected": true,
        "lastBurstAt": "2026-03-12T09:18:31Z",
        "topupCount": 2,
        "intervalSeconds": 20,
        "recentHighTopups": [
          { "eventId": "evt-abc", "amount": 600, "timestamp": "...", "source": "card_ending_1234" },
          { "eventId": "evt-def", "amount": 750, "timestamp": "...", "source": "card_ending_1234" }
        ]
      }
    }
  }
}
```

**Full pipeline**:
```javascript
// Source from Kafka with timeField (required for windowed processing)
let source = {
  $source: {
    connectionName: "UtilitymskKafkaConnection",
    topic: "FuelRetail-fraud-events",
    timeField: { $toDate: "$timestamp" },
    partitionIdleTimeout: { size: 5, unit: "second" }
  }
};

// Filter to auto_topup events >= RM500
let matchHighTopups = {
  $match: {
    name: "auto_topup",
    "properties.amount": { $gte: 500 }
  }
};

// Inside the tumbling window: group by user, count topups, collect details
let groupByUser = {
  $group: {
    _id: "$user_id",
    topupCount: { $sum: 1 },
    firstTopupAt: { $min: "$timestamp" },
    lastTopupAt: { $max: "$timestamp" },
    recentHighTopups: {
      $push: {
        eventId: "$eventId",
        amount: "$properties.amount",
        timestamp: "$timestamp",
        source: "$properties.source"
      }
    }
  }
};

// Only emit when 2+ topups detected in window
let matchCluster = { $match: { topupCount: { $gte: 2 } } };

// Compute time between first and last topup
let computeInterval = {
  $addFields: {
    intervalSeconds: {
      $dateDiff: {
        startDate: { $toDate: "$firstTopupAt" },
        endDate: { $toDate: "$lastTopupAt" },
        unit: "second"
      }
    }
  }
};

// 1-min tumbling window (production: 15 min)
let tumblingWindowStage = {
  $tumblingWindow: {
    interval: { size: 1, unit: "minute" },
    pipeline: [ groupByUser, matchCluster, computeInterval ]
  }
};

// Reshape for user_profiles merge — write detection state under fraud.signals.s01
let projectForMerge = {
  $project: {
    userId: "$_id",
    "fraud.signals.s01.topupBurstDetected": { $literal: true },
    "fraud.signals.s01.lastBurstAt": "$lastTopupAt",
    "fraud.signals.s01.topupCount": "$topupCount",
    "fraud.signals.s01.intervalSeconds": "$intervalSeconds",
    "fraud.signals.s01.recentHighTopups": "$recentHighTopups"
  }
};

// Merge INTO user_profiles — updates existing user doc, doesn't create new ones
let mergeStage = {
  $merge: {
    into: {
      connectionName: "FuelRetail_cluster",
      db: "FuelRetail_fraud",
      coll: "user_profiles"
    },
    on: "userId",
    whenMatched: "merge"
  }
};

sp.createStreamProcessor("FuelRetail-signal-s01a", [
  source, matchHighTopups, tumblingWindowStage, projectForMerge, mergeStage
]);
```

#### S01b — Transfer After Cluster (Windowless)

```
MSK → filter InstantTransfer_transfer_out → $lookup user_profiles → read S01a state →
  cluster detected? → transfer within 30 min of cluster? → build alert → $merge → fraud_alerts
```

**How it reads/writes**: S01b READS from `user_profiles` using `$lookup` to check the detection state that S01a wrote. The `$lookup` uses `connectionName` inside `from: {}` — this is an ASP-specific syntax (different from standard MongoDB `$lookup`). If the conditions match, it WRITES a new alert document to `fraud_alerts` via `$merge`.

**The cross-pipeline state handoff**:
1. S01a writes `fraud.signals.s01.topupBurstDetected = true` to user_profiles
2. S01b reads that field via `$lookup` when a `InstantTransfer_transfer_out` event arrives
3. S01b checks: Was the transfer within 30 minutes of `lastBurstAt`?
4. If yes → write alert to `fraud_alerts` → change stream triggers agent

**Full pipeline**:
```javascript
// Source from Kafka (windowless — no timeField)
let source = {
  $source: {
    connectionName: "UtilitymskKafkaConnection",
    topic: "FuelRetail-fraud-events"
  }
};

// Filter to InstantTransfer transfer out events
let matchTransfers = { $match: { name: "InstantTransfer_transfer_out" } };

// $lookup — READ from user_profiles to get S01a detection state
// NOTE: connectionName must be INSIDE from: {}, not alongside it (ASP gotcha)
let lookupUserProfile = {
  $lookup: {
    from: {
      connectionName: "FuelRetail_cluster",
      db: "FuelRetail_fraud",
      coll: "user_profiles"
    },
    localField: "user_id",
    foreignField: "userId",
    as: "userProfile"
  }
};

let unwindProfile = { $unwind: "$userProfile" };

// Check: did S01a detect a top-up cluster for this user?
let matchClusterDetected = {
  $match: { "userProfile.fraud.signals.s01.topupBurstDetected": true }
};

// Check: is this transfer within 30 min of the cluster?
let matchWithinWindow = {
  $match: {
    $expr: {
      $lte: [
        { $dateDiff: {
            startDate: { $toDate: "$userProfile.fraud.signals.s01.lastBurstAt" },
            endDate: { $toDate: "$timestamp" },
            unit: "minute"
        }},
        30
      ]
    }
  }
};

// Build the alert document with all context
let buildAlert = {
  $addFields: {
    alertId: { $concat: ["alert-s01-", { $toString: "$user_id" }, "-",
               { $toString: { $toDate: "$_ts" } }] },
    userId: "$user_id",
    signal: "S01",
    severity: "critical",
    status: "open",
    details: "Auto top-up >= RM500 x 2+ within 15min + InstantTransfer transfer out within 30min",
    ruleSnapshot: {
      topupAmountThreshold: 500, topupCountThreshold: 2,
      topupWindowMinutes: 15, transferWindowMinutes: 30
    },
    // Combine the topup events from S01a state with the transfer event
    events: {
      $concatArrays: [
        "$userProfile.fraud.signals.s01.recentHighTopups",
        [{ eventId: "$eventId", name: "$name", amount: "$properties.amount",
           timestamp: "$timestamp", properties: "$properties" }]
      ]
    },
    createdAt: { $toDate: "$_ts" }
  }
};

let projectAlert = {
  $project: {
    alertId: 1, userId: 1, signal: 1, severity: 1, status: 1,
    details: 1, ruleSnapshot: 1, events: 1, createdAt: 1
  }
};

// WRITE to fraud_alerts — this triggers the change stream
let mergeStage = {
  $merge: {
    into: {
      connectionName: "FuelRetail_cluster",
      db: "FuelRetail_fraud",
      coll: "fraud_alerts"
    }
  }
};

sp.createStreamProcessor("FuelRetail-signal-s01b", [
  source, matchTransfers, lookupUserProfile, unwindProfile,
  matchClusterDetected, matchWithinWindow, buildAlert, projectAlert, mergeStage
]);
```

### Signal S02 — Instant Transfer Payment After Top-Up (Windowless)

**What it detects**: A user tops up their wallet, then immediately makes a large InstantTransfer payment (> RM500) via bank transfer. This is suspicious because the money is leaving the FuelRetail ecosystem — eWallet payments stay internal, but bank transfers move money out.

**How it reads/writes**: S02 READS from `user_profiles` using `$lookup` to check the `fraud.lastTopupAt` field (written by the topup-state-writer processor on every top-up event). If the payment happened within 30 minutes of the last top-up AND exceeds RM500 AND is a bank transfer, it WRITES a new alert to `fraud_alerts`.

**Why windowless**: Each InstantTransfer payment is checked individually the moment it arrives. The "within 30 minutes" condition is a simple timestamp comparison against stored state — no need to aggregate multiple events in a window.

```
MSK → filter InstantTransfer_payment > RM500 AND type != ewallet →
  $lookup user_profiles.fraud.lastTopupAt → within 30 min? →
  build alert → $merge → fraud_alerts
```

**Full pipeline**:
```javascript
let source = {
  $source: {
    connectionName: "UtilitymskKafkaConnection",
    topic: "FuelRetail-fraud-events"
  }
};

// Filter: InstantTransfer payments > RM500, bank transfers only (not ewallet)
let matchPayments = {
  $match: {
    name: "InstantTransfer_payment",
    "properties.amount": { $gt: 500 },
    "properties.type": { $ne: "ewallet" }
  }
};

// READ from user_profiles to check when user last topped up
let lookupUserProfile = {
  $lookup: {
    from: {
      connectionName: "FuelRetail_cluster",
      db: "FuelRetail_fraud",
      coll: "user_profiles"
    },
    localField: "user_id",
    foreignField: "userId",
    as: "userProfile"
  }
};

let unwindProfile = { $unwind: "$userProfile" };

// Check: does user have a recent top-up within 30 min of this payment?
let matchRecentTopup = {
  $match: {
    "userProfile.fraud.lastTopupAt": { $exists: true },
    $expr: {
      $lte: [
        { $dateDiff: {
            startDate: { $toDate: "$userProfile.fraud.lastTopupAt" },
            endDate: { $toDate: "$timestamp" },
            unit: "minute"
        }},
        30
      ]
    }
  }
};

let buildAlert = {
  $addFields: {
    alertId: { $concat: ["alert-s02-", { $toString: "$user_id" }, "-",
               { $toString: { $toDate: "$_ts" } }] },
    userId: "$user_id",
    signal: "S02",
    severity: "high",
    status: "open",
    details: "InstantTransfer payment > RM500 (bank transfer) within 30min after top-up",
    ruleSnapshot: { amountThreshold: 500, windowMinutes: 30 },
    topupInfo: {
      lastTopupAt: "$userProfile.fraud.lastTopupAt",
      lastTopupAmount: "$userProfile.fraud.lastTopupAmount",
      lastTopupType: "$userProfile.fraud.lastTopupType"
    },
    events: [{ eventId: "$eventId", name: "$name", amount: "$properties.amount",
               timestamp: "$timestamp", properties: "$properties" }],
    createdAt: { $toDate: "$_ts" }
```

### Signal S03 — Multiple Fund-Outs After Top-Up (Hybrid: Windowed + Lookup)

**What it detects**: A user tops up their wallet, then makes 2+ fund-out transfers exceeding RM500 each within a short window. This is a variant of the cash-out pattern — instead of InstantTransfer, the money exits via direct fund transfers to external accounts.

**How it reads/writes**: S03 is a **hybrid** pipeline that combines both ASP patterns:
1. **Windowed aggregation**: First, it groups `fund_out_transfer` events in a 2-minute tumbling window and counts how many exceed RM500 per user
2. **$lookup enrichment**: After the window closes, it READS from `user_profiles` to check if the user had a recent top-up (written by topup-state-writer). This is the "was there a preceding top-up?" check
3. If both conditions match (2+ fund-outs in window AND recent top-up), it WRITES an alert to `fraud_alerts`

**Why hybrid**: Pure windowed wouldn't work because you need to correlate the fund-outs with a top-up event that may have happened before the window opened. Pure windowless wouldn't work because you need to count multiple fund-outs over time. The `$lookup` after the window close bridges these two requirements.

```
MSK → filter fund_out_transfer > RM500 → [2-min tumbling window] →
  group by user → count >= 2? → $lookup user_profiles.fraud.lastTopupAt →
  top-up within 60 min? → build alert → $merge → fraud_alerts
```

**Full pipeline**:
```javascript

  $source: {
    connectionName: "UtilitymskKafkaConnection",
    topic: "FuelRetail-fraud-events",
    timeField: { $toDate: "$timestamp" },
    partitionIdleTimeout: { size: 5, unit: "second" }
  }
};

// Filter: fund-out transfers > RM500

  $match: {
    name: "fund_out_transfer",
    "properties.amount": { $gt: 500 }
  }
};

// Inside the window: group by user, count, collect details

  $group: {
    _id: "$user_id",
    fundOutCount: { $sum: 1 },
    totalAmount: { $sum: "$properties.amount" },
    windowEnd: { $max: "$timestamp" },
    fundOutDetails: {
      $push: {
        eventId: "$eventId", amount: "$properties.amount",
        timestamp: "$timestamp", recipient: "$properties.recipient"
      }
    }
  }
};

let matchMultipleFundOuts = { $match: { fundOutCount: { $gte: 2 } } };

// 2-min tumbling window (production: 30 min)
let tumblingWindowStage = {
  $tumblingWindow: {
    interval: { size: 2, unit: "minute" },
    pipeline: [ groupByUser, matchMultipleFundOuts ]
  }
};

// AFTER window closes: READ from user_profiles to check for recent top-up

  $lookup: {
    from: {
      connectionName: "FuelRetail_cluster",
      db: "FuelRetail_fraud",
      coll: "user_profiles"

    localField: "_id",
    foreignField: "userId",
    as: "userProfile"
  }
};

// Check: did user top up within 60 min before the fund-outs?

  $match: {
    "userProfile.fraud.lastTopupAt": { $exists: true },
    $expr: {
      $lte: [
        { $dateDiff: {
            startDate: { $toDate: "$userProfile.fraud.lastTopupAt" },
            endDate: { $toDate: "$windowEnd" },
            unit: "minute"
        }},
        60
      ]
    }
  }
};

let buildAlert = {
  $addFields: {
    alertId: { $concat: ["alert-s03-", { $toString: "$_id" }, "-",
               { $toString: "$$NOW" }] },
    userId: "$_id",
    signal: "S03",
    severity: "high",
    status: "open",
    details: "2+ fund-out transfers > RM500 within 30min after top-up",

    topupInfo: {
      lastTopupAt: "$userProfile.fraud.lastTopupAt",
      lastTopupAmount: "$userProfile.fraud.lastTopupAmount",
      lastTopupType: "$userProfile.fraud.lastTopupType"
    },
    events: "$fundOutDetails",
    createdAt: "$$NOW"
  }
};

let projectAlert = {
  $project: {
    alertId: 1, userId: 1, signal: 1, severity: 1, status: 1,
    details: 1, ruleSnapshot: 1, topupInfo: 1, events: 1,
    fundOutCount: 1, totalAmount: 1, createdAt: 1

};

// WRITE to fraud_alerts

      coll: "fraud_alerts"
```

### ASP Design Patterns Summary

| Pattern | Processors | How it works |
|---------|-----------|-------------|
| **Tumbling Window** | S01a, S03, S04 | Aggregate events over fixed time intervals. Events inside the window are grouped by user and counted. Window must close before results emit. |
| **Windowless Enrichment** | S01b, S02 | Each event is processed individually on arrival. Enriched with stored state via `$lookup` against MongoDB collections. No waiting for windows. |
| **Hybrid (Window + Lookup)** | S03 | First aggregates in a window (count fund-outs), then does a `$lookup` after window closes to check for correlated state (recent top-up). |
| **State via `$merge`** | S01a | Writes intermediate detection state to `user_profiles` using `whenMatched: "merge"` so other pipelines can read it via `$lookup`. |
| **Cross-collection `$lookup`** | S01b, S02, S03 | Reads existing documents from `user_profiles` mid-pipeline. ASP syntax requires `connectionName` inside `from: {}`. |
| **`partitionIdleTimeout`** | S01a, S03, S04 | Flush tumbling windows after 5 seconds of no events on a partition — makes windowed pipelines demo-friendly. |

### Hybrid Simulator Approach

Windowed ASP processors (S01a, S03, S04) need continuous events over the full window interval to flush. For reliable demos, the simulator uses a **hybrid approach**:

1. **Events → EC2 → MSK** (real pipeline): SSH to EC2, produce events via `aiokafka` with IAM auth. Events flow through ASP and appear in `asp_ingested_events`.
2. **Alert → MongoDB** (direct insert): The `fraud_alert` is inserted directly into MongoDB so the change stream fires immediately without waiting for ASP windows to close.

S02 (windowless) works fully end-to-end through ASP without the direct insert — the windowless processor fires immediately when matching events arrive.

## Hopping Windows — Production-Ready Alternative

The demo uses **tumbling windows** for simplicity: fixed-size, non-overlapping intervals that are easy to reason about. However, tumbling windows have a well-known blind spot — events that straddle a window boundary are split across two windows and may never trigger together.

Atlas Stream Processing also supports **hopping windows** (`$hoppingWindow`), which solve this by creating overlapping intervals. Each pipeline's `.js` source file includes a commented hopping window alternative with guidance on trade-offs. Here is the full analysis.

### The Problem with Tumbling Windows

```
Tumbling (15-min):   |----Window 1----|----Window 2----|
Events:                           ▲  ▲
                              14:59  15:01

Result: The two events land in DIFFERENT windows. If the threshold is 2, neither window fires.
```

### How Hopping Windows Fix This

```
Hopping (15-min interval, 5-min hop):
  |------Window A [0:00–0:15]------|
       |------Window B [0:05–0:20]------|
            |------Window C [0:10–0:25]------|

Events at 14:59 and 15:01 both appear in Window B [0:05–0:20]. Detected.
```

A hopping window slides forward by the `hopSize` interval. Every event appears in `interval / hopSize` overlapping windows (e.g., a 15-min window with a 5-min hop means each event is in 3 windows). This eliminates boundary blind spots at the cost of additional processing.

### Per-Pipeline Analysis

#### S01a — Top-Up Cluster Detection

| Aspect | Tumbling (current) | Hopping (alternative) |
|--------|-------------------|----------------------|
| **Window** | 15 min, non-overlapping | 15-min interval, 5-min hop |
| **Blind spot** | Cluster at minute 14 + minute 16 missed | Captured by overlapping window |
| **Duplicate risk** | None | **Low** — `$merge` uses `on: "userId"` + `whenMatched: "merge"`, so overlapping windows overwrite the same `user_profiles` document. Last write wins. |
| **Recommendation** | Good for demo | **Safe for production** — the merge-on-userId pattern naturally deduplicates |

```javascript
// Replace $tumblingWindow with:
$hoppingWindow: {
  interval: { size: 15, unit: "minute" },
  hopSize:  { size: 5,  unit: "minute" },
  pipeline: [ groupByUser, matchCluster, computeInterval ]
}
```

> S01a is the safest candidate for hopping windows because it writes *state*, not *alerts*. Overlapping windows simply refresh the burst detection state more frequently — actually beneficial for downstream S01b lookups.

#### S03 — Fund-Out Layering After Top-Up

| Aspect | Tumbling (current) | Hopping (alternative) |
|--------|-------------------|----------------------|
| **Window** | 30 min, non-overlapping | 30-min interval, 10-min hop |
| **Blind spot** | Fund-outs at minute 29 + minute 31 missed | Captured |
| **Duplicate risk** | None | **High** — writes to `fraud_alerts` without a dedup key. Each overlapping window creates a new alert. |
| **Recommendation** | Good for demo | **Requires dedup strategy** before production use |

**Dedup strategy** — add a deterministic `alertId` and merge on it:

```javascript
// Change the $merge to:
$merge: {
  into: { connectionName: "FuelRetail_cluster", db: "FuelRetail_fraud", coll: "fraud_alerts" },
  on: "alertId",
  whenMatched: "merge"
}
```

This ensures that overlapping windows referencing the same fund-out cluster converge to a single alert document rather than creating duplicates.

#### S04 — Rapid Card Linking

| Aspect | Tumbling (current) | Hopping (alternative) |
|--------|-------------------|----------------------|
| **Window** | 60 min, non-overlapping | 60-min interval, 15-min hop |
| **Blind spot** | Cards linked at minutes 55, 61, 62 — first in window [0–60], others in [60–120]. Neither hits the threshold of 3. **Missed.** | Captured by window [15–75]. |
| **Duplicate risk** | None | **High** — same issue as S03 |
| **Recommendation** | Good for demo | **Requires dedup strategy** before production use |

Same dedup approach applies: merge on a deterministic `alertId`.

#### S02 — Instant Transfer Payment After Top-Up

S02 is **windowless** (per-event enrichment via `$lookup`), so hopping windows do not apply. Each payment is evaluated individually the moment it arrives.

#### S01b — Transfer After Top-Up Cluster

S01b is also **windowless** — it reads state written by S01a via `$lookup`. Hopping windows on S01a actually improve S01b's effectiveness by keeping the burst detection state fresher.

### Window Strategy Recommendations

| Pipeline | Current | Production Recommendation | Dedup Needed? |
|----------|---------|--------------------------|---------------|
| **S01a** | Tumbling 15 min | Hopping 15 min / 5 min hop | No — `$merge` on `userId` handles it |
| **S01b** | Windowless | No change | N/A |
| **S02** | Windowless | No change | N/A |
| **S03** | Tumbling 30 min | Hopping 30 min / 10 min hop | **Yes** — merge on `alertId` |
| **S04** | Tumbling 60 min | Hopping 60 min / 15 min hop | **Yes** — merge on `alertId` |

> **Key takeaway**: Hopping windows are a straightforward upgrade path for production. S01a can switch immediately with no code changes beyond the window definition. S03 and S04 require adding a dedup key to `$merge` — a one-line change per pipeline. This eliminates the boundary blind spot that tumbling windows create, reducing missed detections without architectural changes.

```python
# Watches for new documents inserted into fraud_alerts
async with db["fraud_alerts"].watch(
```

## LangGraph Agent — 3-Stage AI Investigation

When the change stream detects a new fraud alert, it triggers a **LangGraph sequential pipeline** with 4 nodes:

```
fraud_analysis → similar_cases → recommendation → persist
     │                │                │              │
     ▼                ▼                ▼              ▼
  Claude AI       Voyage AI +      Claude AI      MongoDB
  (Anthropic)     Vector Search    (Anthropic)    $merge
                  + Claude AI
```

### Stage 1: Fraud Analysis

**What it does**: Queries the user's profile, recent events (7 days), and past alerts, then asks Claude to analyze the fraud pattern.

**MongoDB queries executed**:
1. `user_profiles.find_one({userId})` — get full profile
2. `events.find({user_id, timestamp >= 7d ago}).sort().limit(50)` — recent activity
3. `fraud_alerts.find({userId}).sort().limit(20)` — alert history

**Claude output**: `fraud_pattern`, `confidence` (0-1), `timeline_analysis`, `key_indicators[]`, `false_positive_likelihood`, `affected_amount_myr`

### Stage 2: Similar Cases (Vector Search)

**What it does**: Generates an embedding of the fraud pattern using Voyage AI, then searches for similar user profiles using Atlas Vector Search.

**MongoDB query executed**:
```javascript
db.user_profiles.aggregate([
  { $vectorSearch: {
      index: "fraud_similarity_index",
      path: "fraud.embedding",
      queryVector: [/* 1024-dim Voyage AI vector */],
      numCandidates: 50,
      limit: 6,
      filter: { "fraud.riskLevel": { $ne: "low" } }
  }},
  { $match: { userId: { $ne: target_user } } },
  { $project: { userId: 1, fullName: 1, fraud: 1, ... } }
])
```

**Claude output**: `similar_profiles[]`, `ring_analysis` (likely_ring, estimated_ring_size), `pattern_frequency`, `typical_resolution`

### Stage 3: Recommendation

**What it does**: Synthesizes the fraud analysis and similar cases into actionable recommendations, considering BNM regulatory requirements.

**Claude output**: `risk_level`, `recommended_action`, `immediate_actions[]`, `investigation_steps[]`, `estimated_exposure_myr`, `regulatory_implications` (bnm_str_required, aml_review_needed, timeline_days)

### Stage 4: Persist

**What it does**: Saves the complete investigation to `fraud_investigations` collection and updates the user profile.

**MongoDB operations**:
1. `fraud_investigations.insert_one(investigation_doc)` — save full report
2. `user_profiles.update_one({userId}, {$set: {lastInvestigationId, lastInvestigatedAt}})` — link to profile

## How It Works

```
User Question → LangChain Agent → MongoDB MCP Server → MongoDB Atlas → Response
                    │                     │
                    ▼                     ▼
              Claude (Bedrock)      find / aggregate / count
              understands FuelRetail     via stdio connection
              terminology
```

The architecture has three components:

1. **LangChain ReAct Agent** — powered by Claude (via AWS Bedrock). Given a system prompt with FuelRetail-specific terminology mappings, it decides which MongoDB operations to execute.

2. **MongoDB MCP Server** — an open-source Model Context Protocol server that exposes MongoDB operations (`find`, `aggregate`, `count`, `collection-schema`, etc.) as tools the LLM can call. Runs as a local stdio process.

3. **Persistent MCP Session** — the agent maintains a single long-lived connection to the MCP server to avoid session teardown issues. The `langchain-mcp-adapters` library converts MCP tools into LangChain-compatible tools automatically.

## Production Considerations — Materialized Views

The demo queries a `user_profiles` collection with ~10,000 documents. This works well for demonstrations, but running an LLM-generated MQL agent against **production collections** (10M+ documents across multiple clusters) introduces real concerns:

| Risk | Why It Matters |
|------|---------------|
| **Unbounded queries** | The LLM might generate a query without filters or limits, triggering a full collection scan on 10M docs |
| **Unindexed sorts** | An `aggregate` with `$sort` on a non-indexed field forces an in-memory sort — blocked if it exceeds 100 MB |
| **Cluster impact** | Expensive queries compete for resources with the production application |
| **Cross-cluster complexity** | FuelRetail's data lives across 2–3 clusters in different Atlas projects. Querying them all in real-time adds latency and operational risk |

### The Solution: Pre-Aggregated Materialized View Collections

Instead of pointing the MCP server at raw production data, create **purpose-built collections** that pre-aggregate the metrics analysts actually ask about. These collections are refreshed on a schedule via **Atlas Scheduled Triggers** and are small enough that any MQL query the LLM generates will be fast and safe.

```
┌─────────────────────┐         ┌──────────────────────┐         ┌──────────────────┐
│ Production Clusters │  ──────▶│ Atlas Scheduled      │  ──────▶│ Materialized     │
│ (10M+ docs each)    │  nightly│ Triggers             │  $merge │ View Collections │
│                     │         │ (aggregation          │         │ (small, indexed, │
│ cluster-1           │         │  pipelines)           │         │  safe to query)  │
│ cluster-2           │         │                      │         │                  │
│ cluster-3           │         └──────────────────────┘         └──────────────────┘
└─────────────────────┘                                                  │
                                                                         ▼
                                                               ┌──────────────────┐
                                                               │ MCP Server       │
                                                               │ (queries only    │
                                                               │  these safe      │
                                                               │  collections)    │
                                                               └──────────────────┘
```

### Atlas Scheduled Trigger — Example

This trigger runs nightly to refresh `mv_daily_registrations`:

```javascript
// Atlas Scheduled Trigger: refresh_daily_registrations
// Schedule: Daily at 00:15 UTC
// Linked Function:
exports = async function() {
  const db = context.services.get("mongodb-atlas").db("FuelRetail_analytics");
  const profiles = context.services.get("mongodb-atlas").db("FuelRetail_screening").collection("user_profiles");

  const today = new Date();
  today.setUTCHours(0, 0, 0, 0);
  const yesterday = new Date(today);
  yesterday.setUTCDate(yesterday.getUTCDate() - 1);

  const pipeline = [
    { $match: { createdAt: { $gte: yesterday, $lt: today } } },
    { $group: {
        _id: null,
        newUsers: { $sum: 1 },
        verifiedUsers: {
          $sum: { $cond: [{ $eq: ["$kyc.status", "verified"] }, 1, 0] }
        },
        premiumUpgrades: {
          $sum: { $cond: [{ $eq: ["$wallet.tier", "premium"] }, 1, 0] }
        },
        kycCompletions: {
          $sum: { $cond: [{ $eq: ["$kyc.status", "verified"] }, 1, 0] }
        },
        avgTimeToVerifyHours: {
          $avg: {
            $cond: [
              { $eq: ["$kyc.status", "verified"] },
              { $dateDiff: { startDate: "$createdAt", endDate: "$kyc.verifiedAt", unit: "hour" } },
              null
            ]
          }
        }
    }},
    { $addFields: { date: yesterday } },
    { $project: { _id: 0 } },
    { $merge: {
        into: "mv_daily_registrations",
        on: "date",
        whenMatched: "replace",
        whenNotMatched: "insert"
    }}
  ];

  await profiles.aggregate(pipeline).toArray();
  console.log(`Refreshed mv_daily_registrations for ${yesterday.toISOString().slice(0, 10)}`);
};
```

A similar trigger refreshes `mv_monthly_activity` at the end of each day, accumulating daily deltas into the monthly document using `$merge` with `whenMatched: "merge"`.

### Multi-Cluster Consolidation

For FuelRetail's production setup (2–3 separate clusters across different Atlas projects), the scheduled triggers can pull from multiple clusters using **Atlas Data Federation** or **dedicated cross-cluster triggers** that read from each source cluster and write to a single analytics database. The materialized view collections serve as the unified layer that the MCP server queries.

# UC3 — Name Screening (Compliance)

> **Owner: Compliance team**
>
> Sanctions screening using Atlas Search fuzzy matching with a custom Malaysian name analyzer.

---

## What This Solves

FuelRetail needs to screen ~10 million user profiles against a curated sanctions list (~2,000 entries). The challenge isn't simple string matching — Malaysian names have unique complexities:

| Category | Sanctioned List (Source) | User Profile (Target) | Why Simple Matching Fails |
|----------|-------------------------|----------------------|---------------------------|
| Malay connectors | Ismail Ibrahim | Ismail **bin** Ibrahim | "bin" / "binti" are honorifics, not part of the legal name |
| Indian connectors | Ravi Ganesan | Ravi **a/l** Ganesan | "a/l" (anak lelaki) / "a/p" (anak perempuan) are prefixes |
| Abbreviations | Muhammad Nasir | **Mohd** Nasir | Muhammad ↔ Mohd ↔ Muhd ↔ Md are interchangeable |
| Name order | Tan Wei Kiat | Wei Kiat **Tan** | Chinese names can appear in either order |
| Typos | Ahmad Razali | **Ahmd** Razali | OCR errors, manual entry mistakes |

---

## Document Schema Design

### `user_profiles` (Fuel Retail_screening) — 10,000 Users

This is the target collection — the 10 million user profiles that must be screened. Each document carries identity, KYC, wallet, and screening state.

```json
  "email": "ismail.ibrahim@gmail.com",
  "phone": "+60121234567",
  "status": "active",

  "kyc": {
    "status": "verified",
    "verifiedAt": "2024-02-10T08:00:00Z",
    "method": "eKYC",
    "documentType": "MyKad",
    "riskLevel": "low"
  },

  "wallet": {
    "balance": 342.50,
    "currency": "MYR",
    "tier": "standard",
    "dailyLimit": 2000.00
  },

  "linkedCards": [
    { "last4": "7823", "type": "visa", "bank": "RegionalBankB", "linkedAt": "2024-05-10T09:00:00Z", "isDefault": true }

  "updatedAt": "2026-03-05T14:22:00Z"

```

Key design decisions:
- **`screening` subdocument** is updated in-place by the batch sweep — `$set` for `riskFlag` and `lastScreenedAt`, `$push` for new matches. No separate screening-results collection needed.
- **`screening.matches[]`** is an array that grows with each sweep. Each entry records which sanctioned name matched, the source list, the relevance score, and how the match was found (primary name vs alias).
- **`fullName`** is indexed by Atlas Search with the custom `malay_name_analyzer` for fuzzy matching, and separately with an `autocomplete` index for type-ahead search in the UI.
- **`dateOfBirth`** is indexed as a `date` type in Atlas Search for optional DOB-based filtering during screening.

### `sanctioned_list` — ~2,000 Entries (55 in Demo)

The source list of sanctioned individuals. Curated from multiple providers (OFAC, BNM, UN Security Council, EU, FATF, Interpol, AUSTRAC).

```json
{
  "fullName": "Ismail Ibrahim",
  "aliases": ["Ismail bin Ibrahim", "Ismail B Ibrahim"],
  "dateOfBirth": "1985-03-15T00:00:00Z",
  "country": "MY",
  "source": "OFAC",
  "category": "Financial fraud",
  "details": {
    "reason": "Money laundering through digital wallet services",
    "referenceId": "OFAC-2026-MY-0042",
    "lastUpdated": "2026-02-25T00:00:00Z"
  },
  "addedAt": "2026-01-20T00:00:00Z",
  "isActive": true
}
```

Key design decisions:
- **`aliases[]`** stores alternative spellings and transliterations. The batch sweep searches both `fullName` and each alias against user profiles — this is what catches variations like "Mohd Nasir" matching "Muhammad Nasir".
- **`source`** identifies the originating sanctions list. The UI shows a breakdown by source so compliance officers see which lists produced the most hits.
- **`category`** classifies the sanction type (financial fraud, money laundering, terrorism financing, sanctions evasion, corruption). Useful for prioritising follow-up.
- Both `fullName` and `aliases` are indexed with the same `malay_name_analyzer` so connectors and abbreviations are normalised consistently in both directions.

### Index Definitions

Two Atlas Search indexes power the screening:

| Index | Collection | Fields | Analyzer |
|-------|-----------|--------|----------|
| `profiles_fuzzy` | `user_profiles` | `fullName` (string + autocomplete), `dateOfBirth` (date) | `malay_name_analyzer` |
| `sanctions_fuzzy` | `sanctioned_list` | `fullName` (string + autocomplete), `aliases` (string + autocomplete), `dateOfBirth` (date) | `malay_name_analyzer` |

The `malay_name_analyzer` uses character filter mappings to strip connectors (`bin`, `binti`, `a/l`, `a/p`, `anak lelaki`, `anak perempuan`) before tokenisation, so "Ismail bin Ibrahim" and "Ismail Ibrahim" produce identical tokens at index time.

---

## How It Works

Atlas Search handles all of these through a **custom Malaysian name analyzer** combined with **fuzzy matching** (Levenshtein distance). The analyzer strips connectors and normalizes abbreviations at index time, so the search comparison operates on clean tokens.

```
┌──────────────────────────────────────────────────────────────────────┐
│                    Atlas Search Index                                │
│                                                                      │
│  Custom Analyzer: malay_name_analyzer                                │
│  ┌───────────────┐    ┌─────────────┐    ┌───────────────────────┐  │
│  │ Char Filters  │ →  │ Tokenizer   │ →  │ Token Filters         │  │
│  │ Strip: bin,   │    │ standard    │    │ lowercase             │  │
│  │ binti, a/l,   │    │             │    │                       │  │
│  │ a/p           │    │             │    │                       │  │
│  └───────────────┘    └─────────────┘    └───────────────────────┘  │
│                                                                      │
│  Index Fields:                                                       │
│  - fullName: string (fuzzy) + autocomplete (edgeGram 2–15)          │
│  - aliases: string (fuzzy) + autocomplete                            │
│  - dateOfBirth: date (secondary discriminator)                       │
└──────────────────────────────────────────────────────────────────────┘
```

### Two Screening Flows

**Flow 1 — Real-Time (check_new_user)**: When a new user registers or updates their profile, their name is immediately searched against the `sanctioned_list` collection using fuzzy matching. Used for onboarding checks — typically <100/day.

```
New user name → $search sanctioned_list (fuzzy, maxEdits: 2)
             → compound: should [fullName, aliases], optional DOB filter
             → return ranked matches with relevance scores
```

**Flow 2 — Batch Sweep (batch_sweep)**: A full sweep of all ~2,000 sanctioned names against the entire `user_profiles` collection. Each sanctioned entry (primary name + aliases) is searched against profiles. Matches above a score threshold (0.5) are flagged in-place on the user profile.

```
For each sanctioned entry:
  For each name (primary + aliases):
    → $search user_profiles (fuzzy, maxEdits: 2)
    → matches above 0.5 score → $set screening.riskFlag = true
    → $push match details to screening.matches[]
```

### Autocomplete

Both collections have an `autocomplete` index (edgeGram tokenization, 2–15 characters) enabling type-ahead search in the UI. As the compliance analyst types, results appear instantly from either the sanctioned list or user profiles.

### Score-Based Flagging

Atlas Search returns a relevance score (`$meta: "searchScore"`) for each match. The system uses a configurable threshold (currently 0.5) to decide whether a match warrants flagging. Scores reflect how closely the tokens match after the analyzer processes both the query and the indexed document.

## Atlas Search Nodes — Process and Memory Isolation

For a production deployment with 10 million user profiles, we recommend running the screening workload on **dedicated Atlas Search Nodes** rather than the default shared infrastructure.

### Why Dedicated Search Nodes?

| Concern | Default (Shared) | Dedicated Search Nodes |
|---------|-----------------|----------------------|
| **Process isolation** | Search queries compete with application reads/writes for CPU | Search workload runs on separate nodes — zero impact on CRUD operations |
| **Memory isolation** | Lucene search index shares RAM with WiredTiger cache | Search indexes stored entirely on search node RAM — no cache pressure on primary nodes |
| **Scaling** | Search capacity tied to replica set tier | Search nodes scale independently — add capacity for weekly sweeps without touching the app tier |
| **Cost optimization** | One instance size for everything | Search nodes can use memory-optimized instances (search indexes are RAM-intensive) while replica set uses IOPS-optimized instances |

### Sizing Estimate for 10M Profiles

The search index covers a single `fullName` field with two index types (fuzzy string + autocomplete) plus a `dateOfBirth` date field:

| Component | Estimated Size |
|-----------|---------------|
| Fuzzy string index on `fullName` | ~1.5–2.5 GB |
| Autocomplete index on `fullName` | ~0.8–1.2 GB |
| Date index on `dateOfBirth` | ~0.2 GB |
| **Total index footprint** | **~2.5–4 GB** |

Recommended starting point: **M30 search nodes** (8 GB RAM) to ensure the full index fits comfortably in memory with headroom for the weekly batch sweep workload. During full sweeps (~2,000 entries × aliases × fuzzy queries), the search nodes absorb the query burst without affecting the primary replica set.

### Sanctions List Index

The `sanctioned_list` collection (~2,000 entries) is small enough that its search index (<50 MB) doesn't require dedicated nodes. It can remain on the shared infrastructure.

## Batch Sweep — Parallelisation Roadmap

The batch sweep currently processes sanctioned entries **sequentially** — each name is searched against `user_profiles` one at a time. Since each `$search` query is independent, this is a straightforward parallelisation opportunity.

**Current approach:**
```
sanctioned_entry_1 → search → flag → sanctioned_entry_2 → search → flag → ...
```

**Proposed approach (asyncio.gather):**
```
┌─ sanctioned_entry_1 → search → flag ─┐
├─ sanctioned_entry_2 → search → flag ─┤
├─ sanctioned_entry_3 → search → flag ─┼─▶ await all → next batch
├─ sanctioned_entry_4 → search → flag ─┤
└─ sanctioned_entry_5 → search → flag ─┘
```

Running 3–5 concurrent queries would reduce wall-clock time roughly proportional to the concurrency level. For example, a 50-entry sanctioned list that takes ~25 seconds sequentially would complete in ~5–8 seconds with 5x parallelism. Atlas Search handles concurrent requests natively — no server-side configuration changes required.

This is marked as a TODO in the codebase (`screening_service.py`) and is a low-risk optimisation. With dedicated search nodes (see above), the concurrent query load is further isolated from application traffic.

## Recent Platform Changes

### Python 3.14 → 3.13 Migration

The backend was migrated from Python 3.14.0 to **Python 3.13.7** to resolve two issues:

1. **Pydantic V1 compatibility warnings** — Python 3.14 triggered `UserWarning: Core Pydantic V1 functionality isn't compatible with Python 3.14 or greater` on every server startup. These warnings are eliminated on 3.13.

2. **Analytics chatbot MCP plumbing** — The original analytics service used ~140 lines of manual session management code to work around an `anyio.BrokenResourceError` in the MCP SDK's stdio client cleanup. On 3.13, we were able to simplify this using `langchain-mcp-adapters`' `load_mcp_tools()` function, reducing the plumbing from ~140 lines to ~36 lines.

**Impact on the rest of the codebase**: None. All backend services (fraud, screening, analytics) use Python 3.10+ syntax exclusively. No code changes were required outside of `analytics_service.py`.

### Analytics Service — Simplified MCP Integration

The UC2 Analytics Chatbot connects a LangChain agent to the **MongoDB MCP Server**, giving the LLM the ability to run arbitrary MongoDB queries (`find`, `aggregate`, `count`, etc.) in response to natural language questions.
